## 零、最新状态模型（2026-11-23 落地）

### 0.1 销售单（母销售单）

**订单状态（4 态）**

| 状态 | 判定 |
|---|---|
| 未处理 | 销售单刚进入淡茶半盏平台，尚未送分发、未生成履约单（未确定拆成几个履约单） |
| 处理中 | 已送分发 / 已生成履约单，存在未办结且未取消的履约单 |
| 已办结 | 其下全部履约单均已办结 |
| 已取消 | 其下全部履约单均已取消（或未处理即被取消） |

**进度聚合（3 个）**：分发进度（未分发 / 分发中 / 分发完成）、履约进度（未履约 / 履约中 / 履约完成）、结算进度（未结算 / 结算中 / 结算完成）；x/y 中 x = 已完成履约单数，y = 有效履约单数（剔除已取消）。

### 0.2 履约单（四块状态）

| 状态块 | 取值 |
|---|---|
| 分发状态（5 态） | 待分发 / 自营待接单 / 分发比单中 / 转派待接单 / 分发已完成 |
| 履约状态（5 态） | 待接单 / 已接单 / 运输中 / 已妥投 / 已确收 |
| 结算状态（收款 × 开票） | 未收款/已收款 × 未开票/已开票，组合展示如「未收款·已开票」 |
| 订单进度（5 态） | 分发中 / 履约中 / 结算中 / 已办结 / 已取消 |

**订单进度判定**（优先级从高到低）：
1. 已取消：订单取消（分发 / 履约状态不再展示已取消）
2. 已办结：收款 + 开票均完成；或已收款后手工办结
3. 结算中：已确收且已发起对账结算
4. 分发中：分发状态 ∈ 待分发 / 分发比单中 / 自营待接单 / 转派待接单
5. 履约中：其余已进入履约的订单

### 0.3 对账结算入口（新增菜单）

新增 **销售 → 销售单管理 → 履约单结算**（`/sales/sales-settlement`）：

| 操作 | 前置条件 | 结果 |
|---|---|---|
| 发起对账结算 | 履约状态＝已确收 | 订单进度 → 结算中（`settlementStarted`） |
| 登记收款 | 已确收 | 收款维度 → 已收款（`settled`，按发货单结算落库） |
| 登记开票 | 已确收 | 开票维度 → 已开票（`invoiceStatus`） |
| 手工办结 | 已收款且未开票 | 订单进度 → 已办结（`closed`） |

> 收款 + 开票均完成时订单进度自动变为已办结。
> 支撑字段：`ExternalOrder.settlementStarted`（已发起对账结算）、`ExternalOrder.closed`（手工办结）；`settleOnTime` 回归纯质量标记（按时/超时积分）。
> 派生函数：`distributeStateOf` / `fulfillStateOf` / `receiveStateOf` / `invoiceStateOf` / `settleStateOf` / `orderProgressOf` / `familyStatesOf`（均在 `src/utils/salesOrderFamily.ts`）。

## 一、模型回顾（历史 · 上一版四维模型）

### 1.1 四维状态口径

| 维度 | 载体 | 值集 | 写入方 |
|---|---|---|---|
| 分发状态 | `ExternalOrder.processStatus` | 未分发（销售单处理，未生成履约单）/ 待分发 / 报备-匹配待确认 / 自营待接单 / 分发比单中 / 转派待接单 / 分发已完成 / 已取消 | orderFlowStore 各 action |
| 履约状态 | `ExternalOrder.fulfillment.stage` | 待接单 / 已接单 / 运输中 / 妥投 / 已确收 / 已取消 | 接单/发货/妥投/确收类 action；合作商链 `partnerStatus` 镜像同步 |
| 结算状态 | 发货单（包裹）`settled` 标记 | 履约单：未结算 / 部分结算 / 已结算（派生） | `settleOrder`（全部或按发货单） |
| 开票状态 | `ExternalOrder.invoiceStatus` | 未开票 / 部分开票 / 已开票 | `registerInvoice` |

取消贯穿：`cancelOrder` 同时写 `processStatus='cancelled'` 与 `fulfillment.stage='cancelled'`。

> 新增前置环节（2026-11-22）：手工录入 / 平台直连推送的销售单先进入「销售单处理」，`processStatus=unprocessed` 且不生成履约单；送去分发 / 拆分送分发后才生成履约单（`pending`）并进入「履约单分发」。

### 1.2 两级聚合（母销售单按履约单聚合）

| 维度 | 聚合档位 |
|---|---|
| 分发 | 未分发 / 分发中 / 分发完成（全部取消 → 已取消） |
| 履约 | 未履约 / 履约中 / 履约完成（全部取消 → 已取消） |
| 结算 | 未结算 / 结算中 / 结算完成 |
| 开票 | 未开票 / 开票中 / 开票完成 |

实现：`salesOrderFamily.ts` 的 `familyStatesOf` / `fulfillStateOf` / `settleStateOf` / `invoiceStateOf`。

## 二、设计合理之处

| # | 评价 | 说明 |
|---|---|---|
| 1 | **三维解耦符合主流范式** | 分发过程（谁来履约）、履约进度（货到哪了）、资金流（结算/开票）拆为三个独立维度，各自演进互不阻塞。旧模型 10 态混杂三个维度（`self_accepted/self_shipped/self_delivered` 既是分发态又是履约态），新模型每个维度单一职责，与电商系统"订单状态 / 履约单状态 / 支付状态"分离的主流设计对齐 |
| 2 | **自营/合作商双链统一口径** | 履约状态一套 6 态贯穿自营链与分发链（`fulfillment.stage` 为共同载体），管理后台、合作商终端、自营工作台共用 `stageOfOrder` / `FULFILLMENT_STAGE_LABELS` 单点口径，避免了旧模型"自营看 processStatus、合作商看 partnerStatus"的语言分裂 |
| 3 | **已取消用贯穿态而非独立单据状态** | 取消不是一个"排他的单据阶段"，而是覆盖分发/履约两个维度的标记——语义准确（取消的订单没有"进度"可言），且实现成本低（一个 action 写两个字段） |
| 4 | **结算粒度与发货粒度对称** | 结算按发货单（包裹）粒度标记，与"履约单下多发货单 → 部分已发货/全部已发货"的需求对称，天然支持部分结算与"结算中"聚合档 |
| 5 | **展示口径收敛到派生层单点** | `fulfillStateOf` / `settleStateOf` / `invoiceStateOf` / `familyStatesOf` 全部集中在 `salesOrderFamily.ts`，页面不再自行比对状态字符串（旧模型 8 个文件各自维护 completed/processed 归并逻辑的问题被消除） |

## 三、问题清单

> 分级：🔴 高（会产生错误数据或矛盾展示）/ 🟡 中（语义隐患或口径不一致）/ 🟢 低（技术债）。所有行号基于提交 `a676531` 的当前代码。

### 🔴 P1 履约状态双真源：`partnerStatus` 与 `fulfillment.stage` 镜像双写

- **现状**：合作商链上履约进度存两份——`advancePartner`（orderFlowStore.ts:1077）同时写 `partnerStatus`（:1099）和 `fulfillment.stage`；`confirmReceipt` 也双写（partnerStatus 仅分发链写）。`purchaseStore.seedDocs` 从 `partnerStatus` 派生包裹，`stageOfOrder` 从 `fulfillment.stage` 派生展示。自营链 `partnerStatus` 恒为 undefined。
- **影响**：双写依赖每个 action 都记得同步。未来新增/修改履约 action 时漏写其一，就会出现"终端显示已接单、详情页时间线显示待接单"的漂移；且无法从类型系统发现（两者是不同枚举）。
- **建议**：收敛为 `fulfillment.stage` 单真源。`partnerStatus` 改为派生只读视图（终端映射层由 `getPartnerFlowOrders` 从 stage 投影生成），或至少在 `patchOrder` 内加一致性断言（partnerStatus 与 stage 不符时告警）。

### 🔴 P2「分发已完成」是派生态却写进存储

- **现状**：规则"履约状态进入已接单及后续 → 分发状态置 `processed`"由 `acceptSelfOrder` / `advancePartner(accepted)` 各自写死（两处都手写 `processStatus: 'processed'`）。
- **影响**：`processed` 本质是 `stage ≥ accepted` 的可推导值，写入存储后成为第二份需要维护的状态。新增履约入口（如未来"联机自动接单"）漏写时，产生"履约已接单但分发状态仍是转派待接单"的矛盾数据，聚合口径（分发聚合数 `distributed`）随之失真。
- **建议**：二选一——① 分发状态只存前置态（pending/report/self_pending/comparing/distribute_pending/cancelled），"分发已完成"在派生层由履约状态推导；② 保留写死但在 `patchOrder` 统一收口：任何写 `fulfillment.stage ≥ accepted` 的 patch 自动补 `processStatus='processed'`（推荐②，改动小且保留现有展示逻辑）。

### 🔴 P3 取消的逆向处理缺失

- **现状**：`cancelOrder`（orderFlowStore.ts:902）只写 `processStatus` + `fulfillment.stage` 两个字段，不清 `compare` 会话、不清 `partnerStatus`、不处理 PO/包裹。
- **影响**：
  1. 比单中（comparing）订单取消后，`compare.deadline` 倒计时与报名列表在合作商终端仍展示（商机报名入口以 `processStatus==='comparing'` 反查），报完名会写入一个已取消订单的报价；
  2. 运输中订单取消后，包裹仍显示运输中、PO 仍是发货状态，没有任何"召回/退货"承接链路——业务上取消一个在途订单必然触发逆向物流，当前模型只能靠人工线下处理；
  3. `partnerStatus` 残留旧值（如 shipping），聚合与筛选已按 processStatus 过滤取消态，但终端映射 `getPartnerFlowOrders` 对取消单返回 `status:'cancelled'`，partnerStatus 残留暂无危害——属于脏数据。
- **建议**：cancelOrder 按 取消时点分级联动——未分发：仅标记；分发比单中：清 compare 会话；已发货（任一包裹 shipped）：作废未发货 PO 包裹 + 已发货包裹标记"取消待召回"，并强制填写原因；已确收：禁止直接取消（当前已禁），引导走销售退货链。

### 🔴 P4 拆分家族母单可被直接取消，且取消后不可见

- **现状**：`cancelOrder` 无 `parentCode` 限制。拆分家族的母单可从详情抽屉直接取消；而母单不参与聚合（`familyStatesOf` 只聚合 `fulfillmentUnitsOf` 的履约单），母单的取消态在任何列表/聚合中都不可见。
- **影响**：出现"母销售单=已取消、其下子履约单照常履约"的暗箱矛盾，且界面上看不到这个矛盾（母单行不显示自己的分发状态药丸）。
- **建议**：`cancelOrder` 对有子履约单的母单直接拒绝（提示"请取消其下履约单"）；或级联取消（母单取消 → 全部子单取消）。推荐前者，配合分发页"逐子单操作"的定位。

### 🟡 P5 履约状态双口径：时间线档 vs 包裹档并存

- **现状**：详情页同一履约单 Tab 中，"销售履约状态"用 `stagePill(stageOfOrder(current))`（SalesOrderDetail.tsx:134，读 `fulfillment.stage`），信息项"履约状态"用 `pill(fulfillStateOf(current, currentPos))`（:124，按包裹推导）。部分包裹妥投时：`deliverSelfShipment` 只在**全部**妥投才把 stage 写成 transit，此阶段 stage 仍是 shipping → 时间线药丸显示"运输中"，信息项药丸显示"部分妥投"。
- **影响**：同一单同一屏两个履约状态药丸不一致，用户会困惑哪个是真的。
- **建议**：统一为包裹档（`fulfillStateOf` 是更精确的口径）：`stageOfOrder` 的 stage 推导改为按包裹计算（对齐 `selfStageOf` 的做法——自营侧已经这么做了），或将详情页时间线药丸改用 `fulfillStateOf`。取其一，消灭第二口径。

### 🟡 P6 结算语义过载与分母口径待确认

- **现状**：
  1. `settleOnTime` 双重含义——既是"是否按时"的质量标记，又在 `settleStateOf` 中当"是否已结算"的布尔用（salesOrderFamily.ts:142：无包裹订单 `settleOnTime !== undefined → 已结算`）；
  2. 结算分母 = 全部非作废包裹（含未发货 shipped 包裹）——"发 2 包结 2 包"显示已结算后，若补发第 3 包，分母变 3、已结算比例倒退为部分结算。
- **影响**：语义过载导致"未结算订单被误判已结算"（只要 settleOnTime 被任何历史原因写入）；分母口径导致结算状态随发货动作回退。
- **建议**：① 新增独立的订单级 `settled?: boolean`（或 `settleStatus`）字段承载"是否已结算"，settleOnTime 回归纯质量标记；② 分母口径二选一并写入规则文档：仅已妥投/已确收包裹参与结算分母（推荐，与"结算只作用于已妥投包裹"的实现一致），未发货包裹不进分母。

### 🟡 P7 开票状态纯手工登记，无依据联动

- **现状**：`registerInvoice(id, 'partial'|'full')` 仅写标记；部分开票没有金额/发货单依据，未发货订单也可开票。
- **影响**：部分开票与部分结算/部分发货无对应关系，报表上"已开票金额"无法核算；开票早于履约在业务上罕见（除预开票场景），缺乏约束易产生脏数据。
- **建议**：① 部分开票关联发货单（按包裹开票，复用包裹 settled 的对称结构）或记录开票金额字段；② 开票前置条件定为"已确收"（预开票场景单独开权限）。

### 🟢 P8 聚合数值分母与聚合文本口径（已按业务口径调整）

- **现状**：母单行 x/y 分母统一为有效履约单数（剔除已取消），聚合文本同样按有效履约单判定；x/y 与状态药丸同行展示。
- **影响**：混合取消场景（如 3 单中 1 单取消、2 单分发已完成）显示「分发完成 2/2」，取消单不阻塞「完成」，数值与文本语义一致。
- **建议**：无需再调整；如需追溯取消单，可在详情保留履约单总数（含取消）与取消记录。

### 🟢 P9 `rejected`（已驳回）是死枚举

- **现状**：`PartnerOrderStatus` 含 `rejected`，合作商终端有"已驳回"TAB（PartnerOrders.tsx STATUS_TABS），但全仓库无任何写入者——合作商退回走 `partnerReturnOrder` 回到待分发，不产生 rejected 单。
- **影响**：TAB 永远为 0，误导终端用户以为存在驳回终态。
- **建议**：二选一——① 删除 rejected 枚举与 TAB；② 补齐链路（接单前"驳回"= 拒绝接单，区别于退回：驳回后订单由管理后台重新分发且记录驳回原因、扣积分）。推荐②，"驳回"与"退回"业务语义确实不同。

### 🟢 P10 状态标签表弱类型

- **现状**：`EXTERNAL_STATUS_LABELS` / `EXTERNAL_STATUS_COLORS` 为 `Record<string, …>`（externalOrders.ts:1003），页面取值拼写错误编译期不报。
- **建议**：改 `Record<ExternalProcessStatus, { label…}>`，配合 `distributeStateOf` 收口取值。

## 五、待业务确认清单

1. **结算分母**：未发货（shipped）包裹是否计入"部分结算"的分母？（当前计入；若不计入则"发 2 结 2"后补发第 3 包不影响已结算状态）
2. **开票前置条件**：开票是否必须在已确收之后？预开票（未发货先开）是否为合法业务场景？
3. **已确收后取消**：当前禁止；实际业务中客户确收后拒付/退货是否走销售退货单而非取消订单？
4. **母单取消策略**：拆分家族母单是"禁止直接取消"还是"级联取消全部子履约单"？
5. **合作商驳回**：是否需要"接单前驳回"终态（区别于退回），驳回是否扣积分？
6. **取消的权限**：当前管理后台任意账号可取消；是否需要权限点（如仅运营主管）与审批？

## 六、附录

### 6.1 分发状态 × 履约状态合法组合矩阵

| 分发状态 | 履约状态可取值 | 说明 |
|---|---|---|
| 待分发 pending | —（未履约） | 未进入履约主体 |
| 报备-匹配待确认 report_match_pending | —（未履约） | 同上 |
| 分发比单中 comparing | —（未履约） | 定标后拆出子单进入转派待接单 |
| 自营待接单 self_pending | 待接单 | 履约状态一般为待接单 |
| 转派待接单 distribute_pending | 待接单 | 同上 |
| 分发已完成 processed | 已接单 / 部分已发货 / 运输中 / 部分妥投 / 妥投 / 部分已确收 / 全部已确收 | 唯一允许多档履约的分发态 |
| 已取消 cancelled | 已取消 | 贯穿，不可逆（当前） |

### 6.2 履约状态流转链（文字版）

```
待接单 ──接单──▶ 已接单 ──发货(包裹shipped)──▶ 运输中 ──全部包裹妥投──▶ 妥投 ──管理后台确认收货──▶ 已确收
   │                  │                            │（部分妥投 → 显示 部分妥投）
   └────────── 取消 ──▶ 已取消 ◀── 取消（已接单/运输中/妥投 阶段均可，已确收后禁止）
```

### 6.3 结算与开票的粒度对称表

| 履约单下的发货单 | 发货档位 | 结算档位 | 开票档位（当前实现） |
|---|---|---|---|
| 0 张 | 已接单 | 未结算（订单级结算除外） | 未开票 |
| 部分 shipped | 部分已发货 | 未结算（无已妥投包裹可结） | 未开票 |
| 全部 shipped | 运输中 | 未结算 | 未开票 |
| 部分 delivered | 部分妥投 | 未结算 / 部分结算 | 未开票 |
| 全部 delivered | 妥投 | 未结算 / 部分结算 / 已结算 | 未开票 |
| 全部 confirmed | 全部已确收 | 未结算 / 部分结算 / 已结算 | 未开票 / 部分开票 / 已开票 |

> 注：开票列是当前实现口径（手工登记无前置约束），"待业务确认清单"第 2 项确认后将收紧。

## 七、结论

四维状态模型的方向是正确的：维度解耦、双链统一、聚合口径集中在派生层，相比旧 10 态混杂模型有本质提升，能够支撑当前演示级业务的全部流转。当前的主要风险集中在**双写一致性**（P1/P2，靠纪律而非机制保证）与**取消/开票的边界规则**（P3/P4/P7，功能缺口而非设计缺陷）。建议按第四节优先级落地"立即修"四项（均为小改动），并尽快确认"待业务确认清单"中的六个口径问题后再做近期项。
