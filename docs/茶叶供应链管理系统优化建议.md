# 茶叶供应链管理系统 · 功能与菜单优化建议

> 基于 2026-10 版代码库（React 18 + TS + zustand + vite）通读分析。覆盖管理后台 9 大模块约 60 个页面、合作商终端、客户终端。
> 文档定位：从整个项目管理出发的问题诊断与优化路线，供产品迭代规划参考。

---

## 一、项目概览与业务链路

### 1.1 系统定位

本系统是「淡茶半盏」茶叶品牌的供应链管理平台，承载**从合作商进货 → 仓储流转 → 销售给客户 → 财务结算**的完整链路，含三个端：

| 端 | 入口 | 核心职能 |
|---|---|---|
| 管理后台 | `/` | 采购、销售、仓储、商品、财务、统计、人员、系统 |
| 合作商终端 | `/partner/login` | 接单/报价/报备/结算/信息维护（品牌商、供应商、服务商三类） |
| 客户终端 | `/customer/login` | 客户自助浏览商品、下单、查订单 |

### 1.2 核心业务链路

```
【进货侧】合作商注册审批 → 合作商档案（品牌商/供应商/服务商）
         → 采购报（调）价 → 采购订单 → 入库管理 → 库存
         → 订单分发至合作商终端 → 合作商接单/发货（直送 or 入合作仓）

【销售侧】销售报（调）价 / 客户报价（VIP 价）→ 销售下单（6 种销售场景）
         → 销售订单 → 出库/直送 → 客户对账 → 销售回款
         其中情况2：淡茶 → 平台客户（扣点）→ 直营客户

【支撑侧】商品档案（8 级价格体系）· 人员绩效（主办人/跟单人）· 财务核算 · 统计分析
```

### 1.3 现状盘点（模块 × 页面）

| 模块 | 页面数 | 核心页面 | 数据现状 |
|---|---|---|---|
| 工作台 | 5 | 首页概览、待办、快捷入口、消息、日志 | 静态 mock（`data/mock.tsx`） |
| 采购 | 7 | 概览、采购订单、报（调）价、入库、合作商管理（2）、对账、退货 | 订单本地 state，概览静态 mock，合作商/审批走共享 store |
| 销售 | 9 | 概览、下单、订单、报备、报价、客户管理、下单账号、对账、退货 | 下单写入模块级 `orderData`，客户管理 store 化，其余 mock |
| 商品 | 9 | 商品管理（4 类目）、分类、品牌、价格管理、新品提醒、茶叶档案 | 商品/价格 store 化较好，新品提醒与终端联动 |
| 仓储 | 9 | 概览、出入库×4、盘点、流水、仓库设置、预警设置 | 全静态 mock，仅仓库设置与合作商仓库联动 |
| 财务 | 9 | 概览、结算×4、发票、成本、费用、余额 | 全静态 mock |
| 统计 | 7 | 销售/品牌/采购/库存/财务/茶类/同比 | 部分从 mock 计算，部分写死 |
| 人员 | 5 | 组织架构、员工、茶人、带货人、门店 | 员工/组织 store 化，绩效函数已实现但未接订单 |
| 系统 | 7 | 设置、角色、日志、用户、备份、单位、关于 | 静态演示 |
| 合作商终端 | 13 | 工作台、订单、报价、报备、客户、结算、账号、设置×6 | 与管理端 store 双向联动（最新完成） |
| 客户终端 | 6 | 工作台、商品、购物车、订单、账号 | 独立 mock，与管理端未打通 |

**已具备的能力亮点**：合作商三类型体系与注册审批流、8 级价格体系（基准价/渠道价/订单实价三层取价）、客户五类型编号体系、销售 6 场景与绩效规则模型、合作商终端与管理后台的实时联动（订单分发、报价、新品提醒、注册审批）、统一的列表/详情/编辑交互规范。

## 二、核心问题诊断

### 2.1 【最关键】业务主链路数据断裂

目前「订单 → 库存 → 财务」三大环节各自为政，均使用独立静态 mock：

| 断点 | 现状 | 影响 |
|---|---|---|
| 采购订单 → 采购入库 | `PurchaseOrders` 新建订单仅存本地 state；`InventoryPurchaseInbound` 使用独立 `mockInboundOrders` | 下了采购单不会产生入库任务，入库数与订单数对不上 |
| 销售订单 → 销售出库 | `SalesOrderCreate` 写入模块级 `orderData`（非响应式）；`InventorySalesOutbound` 使用独立 `mockOutboundOrders` | 出库与订单脱节，且直送/入库两种配送方式无差别处理 |
| 采购订单 → 采购付款 | `FinancePurchasePayment` 使用静态 `paymentItems` | 应付金额与实际订单金额无法核对 |
| 销售订单 → 销售回款 | `FinanceSalesCollection` 使用静态 `collectionItems` | 应收/回款与订单脱节，客户信用额度无从谈起 |
| 库存 → 库存管理台账 | `InventoryStock` 使用静态 `stockItems`；盘点/调拨/其他出入库均为独立 mock | 库存数量不随任何单据变化，预警设置形同虚设 |
| 工作台/统计 | 从 mock 取数 | 概览数字与业务页面数字对不上，失去驾驶舱意义 |

### 2.2 业务规则已定义、系统未承载

项目规则中定义了许多优秀业务模型，但页面层尚未落地：

1. **情况 2（经平台转售）无链路承载**：规则定义了「淡茶→平台客户→直营客户」及平台扣点计算，但销售下单页只能选一个客户，无「关联平台客户」「平台扣点」字段，绩效与利润的分账计算没有触发入口。
2. **绩效自动计算未接入**：`calculateEmployeePerformance` 函数已实现（按 6 场景、主办人 50%/90%、跟单人 40%、利润 87% 分成），但销售订单确认后并不生成绩效记录，员工管理页绩效数据与订单无关。
3. **两种合作模式无差异化结算**：供应商（差价模式）与服务商（扣点模式）的结算逻辑应不同，但「供应商对账」与合作商终端「结算」页均为静态，未按模式区分。
4. **订单分发闭环不完整**：合作商终端「订单」页展示平台分发订单（mock），管理端采购侧没有「分发订单给合作商」的操作入口，两边的订单状态（pending→accepted→shipping→delivered）没有状态同步机制。
5. **报备转订单断链**：合作商终端提示「报备审批通过后自动转入订单」，但管理端「报备管理」的审批动作不会生成订单或推送到终端。

### 2.3 菜单与信息架构问题

1. **术语未统一**：合作商体系改造后，采购菜单仍保留「供应商对账」，与「合作商管理」并排易混淆（对账对象其实是全部三类合作商）。
2. **父级菜单无落地页**：「库存管理」（inventory-stock）、「结算管理」（finance-settlement）为带子项的父菜单但无对应路由/落地页，点击体验不完整。
3. **孤儿页面冗余**：`ProductGrade`（品级管理）、`ProductList`、`PurchaseQuality`（质检管理）、`InventoryTraceability`（溯源管理）、`InventoryStock`（库存管理）等页面文件存在但未挂任何菜单/路由，属于历史遗留，其中品级、质检、溯源恰是茶叶行业高价值功能，建议恢复入口而非埋没。
4. **门店管理归属模糊**：门店管理挂在「人员」模块下（`personnel-stores` 实际渲染的是 `SalesStores` 组件），但门店与销售出库、仓库设置（门店仓）联动更紧密，归属错位。
5. **对账功能分散**：供应商对账在采购、客户对账在销售，而财务模块又有结算管理，三处口径不一，缺少统一对账中心。
6. **工作台未成为统一待办中心**：注册审批、报备审批、新品提醒处理、库存预警分散在各模块，工作台「待办事项」为静态列表，未聚合真实待办。

### 2.4 数据与工程一致性问题

1. `SalesOrders.tsx` 中 `orderData` 为**模块级可变数组**（`export const` + `unshift`），非 zustand 状态，跨页面不响应、刷新即丢失，是销售链路联动的最大隐患。
2. mock 数据（`data/mock.tsx`）与 store 数据（`supplierStore`、`customerStore` 等）双轨并存，同类业务两套数据源。
3. 审批流（注册审批）已跑通，但报备审批、调价审批、订单审批各自实现，无统一审批模型。

## 三、优化建议

### 3.1 P0：打通业务主链路（价值最高）

| # | 建议 | 具体方案 | 涉及页面 |
|---|---|---|---|
| 1 | **采购订单 → 入库单联动** | 采购订单确认后自动生成「待入库」单据（含订单号、商品、数量、目标仓）；入库单可关联采购订单带出明细，确认入库回写订单「已入库数量」，部分入库支持分批 | PurchaseOrders、PurchaseInbound、InventoryPurchaseInbound |
| 2 | **销售订单 → 出库单联动** | 销售订单确认后按配送方式分流：直送订单（direct）生成「直送任务」推给对应合作商终端；入库订单（warehouse）生成「待出库」单，出库确认扣自有仓库存 | SalesOrders、SalesOrderCreate、InventorySalesOutbound、PartnerOrders |
| 3 | **订单 → 财务收付联动** | 采购订单确认生成应付（待付款）、销售订单确认生成应收（待回款）；收付款核销后回写订单结清状态；对账单据由订单汇总生成而非静态 | FinancePurchasePayment、FinanceSalesCollection、采购/销售对账页 |
| 4 | **库存台账统一** | 以出入库流水为唯一事实来源汇总库存（商品 × 仓库 × 批次）；盘点盈亏自动生成「其他出入库」单；预警设置实时作用于台账产生预警项 | InventoryStock、InventoryCheck、InventoryOtherIO、InventoryAlertSettings |
| 5 | **销售订单数据 store 化** | 新建 `orderStore`（zustand）承载销售订单/采购订单，替换 `orderData` 模块级数组；概览、统计、财务从 store 派生计算 | SalesOrders、SalesOrderCreate、各 Overview、Statistics* |
| 6 | **工作台升级为真实驾驶舱** | 首页概览数字全部由 store 计算；「待办事项」聚合注册审批、报备审批、新品提醒、库存预警、逾期应收五类真实待办，点击直达处理页 | DashboardOverview、DashboardTodo |

### 3.2 P1：补齐业务规则承载与菜单优化

| # | 建议 | 具体方案 |
|---|---|---|
| 7 | **情况 2 平台链路落地** | 客户档案（platform 类型）增加「平台扣点」字段；销售下单时若选「直营客户 + 关联平台客户」，订单自动按 (1-扣点) 计算平台侧金额，并驱动绩效与利润分账；订单列表增加「平台单」筛选 |
| 8 | **绩效自动化** | 销售订单审批通过后按 6 场景规则自动生成绩效记录（含主办人/跟单人比例），员工管理页绩效 Tab 改为从订单派生的月度汇总，支持按人/按单穿透查看 |
| 9 | **合作商差异化结算** | 按合作模式生成月度结算单：供应商=采购实价合计（差价模式）；服务商=售价×(1-扣点)服务费分账（扣点模式）；「供应商对账」更名「合作商对账」并按类型分组，与合作商终端「结算」页同源 |
| 10 | **订单分发闭环** | 采购模块新增「订单分发」入口（或将采购订单关联合作商下发）：管理端下发 → 终端接单/发货 → 状态实时同步；终端发货后直送单自动流转为完成 |
| 11 | **报备转订单** | 报备审批通过后自动在销售订单创建「报备转入单」（仅同步展示），并推送合作商终端，实现提示文案承诺的闭环 |
| 12 | **菜单信息架构调整** | 见下文 3.3 对照表 |
| 13 | **孤儿页面归位** | 品级管理（ProductGrade）挂入「商品」菜单；质检管理（PurchaseQuality）挂入「采购」子菜单；溯源管理（InventoryTraceability）挂入「仓储」子菜单；ProductList 等确认废弃后删除 |
| 14 | **门店管理归位** | 门店管理从「人员」移至「销售」模块（与客户仓库、门店仓联动）；人员模块保留组织/员工/茶人/带货人 |

### 3.3 菜单结构优化对照表

| 模块 | 现状 | 建议 |
|---|---|---|
| 采购 | 概览 / 采购订单 / 采购报（调）价 / 入库管理 / **合作商管理**（注册审批、合作商列表）/ **供应商对账** / 采购退货 | 「供应商对账」→「合作商对账」；新增子菜单「质检管理」；「入库管理」与仓储「采购入库」二选一保留（建议采购侧保留入库执行、仓储侧保留台账视角） |
| 销售 | 概览 / 下单 / 订单 / 报备 / 报价 / 客户管理 / 客户下单账号 / 客户对账 / 退货 | 从「人员」移入「门店管理」；「客户对账」与财务「销售回款」做数据同源；新增「平台单管理」视图（情况 2 链路） |
| 商品 | 概览 / 商品管理 / 分类 / 品牌 / 价格 / 新品提醒 / 茶叶档案 | 新增「品级管理」（恢复 ProductGrade），与价格体系中的 pricingFactor 打通 |
| 仓储 | 概览 / 库存管理（父，无落地）/ 出入库×4 / 盘点 / 流水 / 仓库设置 / 预警 | 「库存管理」父菜单补库存台账落地页（P0-4 的产物）；新增「批次溯源」 |
| 财务 | 概览 / 结算管理（父，无落地）/ 发票 / 成本 / 费用 / 余额 | 「结算管理」父菜单增加汇总落地页（应收/应付/净利一览）；成本核算接入订单实价与库存成本 |
| 人员 | 组织 / 员工 / 茶人 / 带货人 / **门店管理** | 移出门店管理；员工管理绩效数据与订单打通（P1-8） |
| 统计 | 7 个分析页 | 数据源改造后全部改为 store 派生；新增「合作商分析」（分类型的采购/履约/结算贡献） |
| 系统 | 设置 / 角色 / 日志 / 用户 / 备份 / 单位 / 关于 | 「操作日志」与工作台日志合并统一；角色权限与菜单/数据范围绑定做实 |

### 3.4 P2：面向茶叶行业的增值功能

1. **批次与效期管理**：茶叶是强批次、强效期商品（春茶/明前、保质期 12-18 月），建议库存台账引入批次号 + 生产日期 + 效期，出库按先进先出，临期自动预警——与现有溯源页面（InventoryTraceability）合并为「批次溯源中心」。
2. **客户终端与管理端订单打通**：客户终端下单进入 `orderStore`，走销售订单同一链路（取价优先级 VIP价>销售价>市场价），「客户下单账号」页管理终端账号开通。
3. **统一审批中心**：注册审批、报备审批、调价审批、订单审批抽成统一审批模型（类型/载荷/状态机），工作台待办与各模块审批页共用。
4. **对账单推送与导出**：对账单一键导出 Excel/PDF，合作商终端支持在线确认对账单（确认后锁定）。
5. **消息通知中心打通**：`notifications` mock 替换为事件驱动（审批结果、订单状态变更、库存预警、新品提醒处理结果），工作台与终端角标统一。
6. **报表订阅**：经营日报/周报（销售、毛利、库存周转）定时推送给管理层角色。

### 3.5 工程与数据治理建议

1. **数据层收敛**：以「合作商/客户/订单/库存/财务」5 个核心 store 为骨架，`data/mock.tsx` 逐步降级为种子数据（seed），所有 Overview/统计页从 store 派生，杜绝同名数据双轨。
2. **操作留痕**：关键写操作（订单确认、审批、盘点、调价）统一写入操作日志，支撑审计与「操作日志」页面真实化。
3. **权限落地**：`SettingsRoles` 的角色配置与菜单可见性、数据范围（如销售只看自己客户）绑定，作为上线前置条件。
4. **字段补全**：客户信用额度与账期（支撑回款逾期）、商品成本价（支撑成本核算与毛利）、仓库库容（支撑入库校验）。

## 五、小结

本系统在**主数据与规则建模**上已有很好的底子：合作商三类体系、8 级价格、客户五类型、销售六场景与绩效规则都是清晰的领域模型；合作商终端与管理后台的双向联动是全项目完成度最高的闭环。

当前最大的短板是**单据流断裂**：订单、库存、财务三段各自为政，导致概览与统计失去可信度。建议以「一套订单 store + 单据自动流转」为第一阶段主线，先让数字在系统内部自洽，再逐步叠加平台链路、绩效、结算等规则承载与行业化增值能力。
