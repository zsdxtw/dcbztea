## 一、项目概览

### 1.1 系统定位

「淡茶半盏」茶行业 ERP 是一套面向茶叶品牌/供应链企业的多端业务中台，承载 **外部平台订单归集 → 分流决策（自营/合作商分发）→ 履约执行 → 财务结算 → 合作商运营** 的完整业务闭环，目前为**纯前端高保真原型**（无后端，mock 数据驱动）。

### 1.2 技术栈

## 二、核心业务内容与逻辑

### 2.1 订单处理中枢（2026-10 新增，系统核心）

订单统一入口，状态机全程可追溯：

```
手工录入 / 平台直连推送 ──→ 待处理
    ├─ 命中已审批报备 ──自动──→ 分发待接单（分发-报备）
    ├─ 选自营 ──→ 自营待接单 ──管理后台接单(填跟单人+选采购供应商，生成采购单)
    │              └─→ 已处理（采购中→已入库→已发货）→ 已完成
    └─ 选分发 ──┬─ 指定 ──即时──→ 分发待接单（分发-指定）
                ├─ 抢单 ──→ 抢单中（合作商先到先得，倒计时，超时退回）
                └─ 比单 ──→ 比单中（公开报名制）
                            · 发起时设定底价（折扣%或具体价格）
                            · 全体合作商限期内报名，报价默认带出其系统报价（品牌折扣）
                            · 报价不得低于底价（前后端双重校验）
                            · 截止按「报价50%+积分50%」评分定标，支持直接选定
                            └─→ 分发待接单（分发-抢单 / 分发-比单）
分发待接单 ──合作商终端接单──→ 已处理（发货→签收→结算）→ 已完成（结算写积分）
```

配套机制：
- **重新流转**：未接单订单可退回待处理重选路径；已接单需二次确认（已发货等状态分级警示）；重新流转清除报备匹配，不再自动分发
- **路径调整全程留痕**：轨迹记录每个动作（录入/转出/接单/延长/定标/选定/修改/重新流转/结算）

### 2.2 合作商积分体系（比单评分数据源）

四维台账：**客户拜访**（终端打卡 +2/次）+ **报备情况**（审批通过 +5、转单完成 +10）+ **履约情况**（按时 +5 / 超时 −5）+ **处罚情况**（投诉 −10、违约 −20）；期初分快照 + 流水累加，参与比单评分，形成「履约越好 → 积分越高 → 比单越易中单」的正向激励闭环。

### 2.3 价格体系（8 级）

商品基准价（市场/天猫/京东/销售价，商品管理维护）→ 采购价规则（商品×供应商，折扣率联动）→ 销售报价（商品×客户 VIP 价，经平台客户自动算平台实得价）。价格管理页调价通过 priceStore 联动更新全链冗余字段。

### 2.4 合作商三类型与注册审批流

品牌商（平台直接合作）/ 供应商（差价模式）/ 服务商（扣点模式）；终端注册 → 管理端审批 → 档案入库（HZS 编号）→ 终端账号体系（管理员+操作员）；资质文件、仓库、门店、开票、结算银行账户全套档案。

### 2.5 其余模块

- **采购**：采购订单/报调价/入库/对账/退货 + 合作商门店地图总览（地区/品牌筛选，近期开发热点）
- **销售**：客户管理（五类型：直营/渠道/平台/个人/带货，下单人/分子机构/分润比例）、客户下单账号开通、客户对账
- **仓储**：出入库四类 + 盘点 + 调拨 + 预警规则 + 仓库设置（独立/门店/合作三类仓库）
- **商品**：四类目商品管理（茶叶/茶具/周边/其他，含箱规/条码/上下架）+ 品牌 + 分类 + 新品提醒（合作商提报→管理端处理）
- **财务**：结算四类（采购付款/销售回款/其他应收应付）+ 发票 + 成本 + 费用 + 余额
- **统计**：销售/品牌/采购/库存/财务/茶类/同比七维分析
- **人员**：组织架构树 + 员工（合同/身份证/学历/结算）+ 茶人（证书/获奖/服务报价）+ 带货人 + 门店
- **客户终端**：直营客户购物车式自助下单，管理台确认/发货/结算联动

## 三、优点分析

1. **业务建模深度突出**。1500 行 TypeScript 类型字典即业务术语表：6 种销售场景、8 级价格、3 类合作商、5 类客户、分润三角色（拓客/维护/跟单）、直营客户下单人与分子机构……对茶叶流通行业的业务抽象密度远超一般原型，具备直接向真实系统迁移的领域模型基础。

2. **订单分流中枢设计完整且有业务巧思**。报备匹配复用/自营背对背以销定采/指定·抢单·比单三分发方式/底价保护的公开报名制比单/积分定标——「比单 + 积分」组合在通用 ERP 中罕见，贴合产业带多供应商竞价协同的真实诉求，是潜在的差异化卖点。

3. **三端协同闭环（演示级）完整**。管理台开通账号 → 终端登录 → 报备/报价/抢单/报名 → 审批/定标 → 接单履约 → 结算回写积分，全链路在同一运行时可走通，业务演示与培训价值高。

4. **交互与视觉规范统一**。DetailDrawer 详情抽屉规范（查看/编辑双态、底部操作区）、模块主题色体系（body[data-module] 切换九套令牌）、流程图式状态栏、统一状态标签/药丸组件——60+ 页面观感一致，维护成本低。

5. **工程习惯良好**。TS 严格编译零错误、提交信息规范（conventional commits）、mock 与页面分离（data/ 目录）、跨端逻辑收敛在 store 而非页面。

## 四、缺点与风险分析

### 4.1 架构性短板

| # | 问题 | 影响 | 严重度 |
|---|---|---|---|
| 1 | **纯前端 mock、无持久化** | 刷新即重置，无法承载任何真实业务；「演示品」天花板 | ★★★★★ |
| 2 | **主链路数据断裂**（docs 已诊断） | 订单处理中枢已贯通「入口→分流→履约」，但仓储出入库、财务结算仍是独立静态 mock，未与订单联动；订单处理里的「入库/出库/结算」只是状态推进 | ★★★★☆ |
| 3 | **无鉴权无安全** | 管理后台无登录；终端密码明文存 mock/localStorage；无 RBAC（角色权限页是摆设） | ★★★★☆ |
| 4 | **并发语义缺失** | 抢单「时间优先」在单机 store 上模拟，真实多合作商并发抢同一单必须后端原子操作；比单报名同理 | ★★★☆☆ |
| 5 | **性能** | 单 bundle 2.2MB（ECharts 全量、无路由级代码分割），首屏慢；巨型页面文件（如合作商列表 4600 行）改一处全页热更 | ★★★☆☆ |
| 6 | **无测试** | 331 次提交零测试文件；状态机、积分计算、报备匹配这类纯逻辑最适合单测却未覆盖 | ★★★☆☆ |

### 4.2 数据与体验问题

- 种子数据分散在 20 个 data 文件（6.5K 行），实体间靠名称字符串互查（如报备按合作商名称匹配 ID），脆弱
- 客户终端与管理端客户档案未完全打通（独立 mock）
- 电商平台「直连推送」渠道目前只是种子标注，无真实对接设计（webhook/API 的字段映射、幂等、对账）

### 4.3 演进方式风险

提交历史中大量「feat: update workspace」式生成迭代，功能堆叠快但容易重复造轮子（如本次订单处理即重写了两版入口页）；缺少 PR 评审与设计文档沉淀（docs 仅一份诊断）。

## 五、市场需求分析

**行业背景**：中国茶叶内销规模约 3000 亿元/年，流通端有数十万家茶企/茶店/茶城商户；行业数字化率显著低于食品饮料平均——上游种植端和零售门店端有零星 SaaS，但**「品牌方-多合作商-多渠道客户」的中游供应链协同层基本空白**。

**目标客群（按贴合度排序）**：
1. **区域茶叶品牌/供应链公司**（最贴合）：自有品牌 + 十到数百家供货/服务商 + 直营/渠道/平台客户混合销路——正是本系统的三类型合作商 + 五类客户 + 平台扣点模型
2. **茶产业带服务商**（如福州/安溪/杭州茶都）：需要订单分发、比价、账期结算工具
3. 中小茶企：需要轻量进销存，但本系统对其偏重

**竞争格局**：通用 ERP（金蝶/用友/管家婆）太重、实施贵、不懂茶；垂类竞品集中在门店 POS 与电商 ERP（聚水潭等）。「**报备保护 + 抢单/比单分发 + 积分运营**」的组合在茶行业乃至 B2B 分销领域都是稀缺能力。

**核心机会**：把「合作商协同层」做成标准品——这正是本项目已经建好的部分。

## 六、继续开发建议与策略

### 总体判断

当前项目处于**「高保真业务原型」阶段**：领域模型完整、流程闭环、演示力强，最大资产是业务抽象而非代码本身。继续开发的正确姿势是**「冻结原型广度、纵深打通数据链路、逐步后端化」**，而非继续横向加功能页。

### 三阶段路线图

**P0 · 原型收口（2-4 周，零后端依赖）**
1. 主链路 mock 贯通：订单处理的入库/出库/结算动作真实写入仓储/财务 mock（共享 store），统计页改由真实数据计算——消灭「演示时数据对不上」的尴尬
2. 客户终端与管理端客户档案打通（复用 customerStore）
3. 种子数据治理：统一 ID 引用，去掉按名称互查
4. 巨型页面拆分 + 路由级代码分割（bundle 预期降 40%+）
5. 为状态机/积分/报备匹配/比单评分补 Vitest 单测（纯函数，成本低收益高）

**P1 · 后端化（1-2 月，成为可用系统）**
1. 技术选型建议：**轻后端优先**——NestJS/Express + Prisma + PostgreSQL（或先用 Supabase 快速验证），前端 store 层已就位，只需把「读种子」换成「读 API」
2. 三端真实账号体系：JWT + RBAC（角色权限页现成模型直接启用），管理后台补登录
3. 抢单/比单后端原子化（事务 + 行锁/Redis），积分台账幂等写入
4. 电商直连通道：先接抖音/天猫开放平台订单推送（webhook 落库 → 进「待处理」池），做字段映射与幂等
5. 数据权限：合作商只能见自己名下订单/客户

**P2 · 产品化与商业化（3 月+）**
1. **移动化**：合作商端做微信小程序（接单/抢单/比单报名/拜访打卡天然适合手机）；客户终端小程序商城化
2. **积分运营深化**：积分规则可配置化、积分商城/返利，让「比单-积分」飞轮转起来
3. **BI 与经营分析**：统计模块接入真实数据，做品牌/合作商/茶类维度的经营驾驶舱
4. **SaaS 多租户**：以「淡茶半盏」自营业务先行跑通 6 个月，沉淀模板后按产业带地推输出

### 商业策略建议

- **先自用后外售**：本系统业务模型疑似源自真实业务（淡茶半盏自身），先让自家业务成为标杆客户，验证「比单+积分」协同模式的实际效果数据
- **差异化定位**：对外叙事聚焦「茶叶供应链协同平台（订单分发/比单/积分/三端协同）」，避开与通用 ERP 和门店 POS 的正面竞争
- **定价锚点**：按合作商席位/订单量阶梯订阅（SaaS），替代 ERP 买断制，降低中小茶企门槛
- **风险对冲**：警惕头部客户定制化陷阱（定制需求走配置化而非改核心）；直连推送依赖平台开放政策，需保留手工录入兜底（已具备）
