# 状态机设计评审文档

## Context

刚完成销售单/履约单状态体系重构（分发 7 态 / 履约 6 态 / 结算按发货单 / 开票 / 已取消贯穿 / 母单四维聚合，提交 a676531）。需要对该设计做合理性分析，指出问题并给出建议，形成评审文档存入 `docs/`。

产出物：**`docs/销售单状态机设计评审.md`**（纯文档，不改代码）。

## 文档结构

1. **背景与模型回顾** — 四维状态口径总表（分发/履约/结算/开票+取消）、两级聚合规则、代码位置（types/index.ts、orderFlowStore.ts、salesOrderFamily.ts、fulfillment.ts）
2. **设计合理之处**（5 点）— 维度解耦（分发过程/履约进度/资金流三轨分离，对齐主流电商订单模型）；自营/合作商双链统一口径；取消贯穿而非独立态；结算粒度与发货粒度对称；派生层收敛（fulfillStateOf/settleStateOf/invoiceStateOf 单点口径）
3. **问题清单**（按 高/中/低 分级，每条含现状→影响→代码位置，均已核实）：
   - **P1 履约状态双真源**：`partnerStatus` 与 `fulfillment.stage` 镜像双写（advancePartner/confirmReceipt 各写两份），任何一处漏写即漂移 → 建议收敛为 stage 单真源、partnerStatus 派生化
   - **P2 分发已完成是派生态却写进存储**：`processed = f(stage≥accepted)` 双写，新 action 漏写即出现"履约已接单但分发待接单"矛盾数据 → 建议派生化或加一致性断言
   - **P3 取消的逆向处理缺失**：cancelOrder 不清 `compare` 会话（比单倒计时残留）、不动 PO/包裹（取消运输中订单包裹仍在途且无召回链路）、不清 partnerStatus；已确收后不可取消但实际业务"确收后取消"应走退货链
   - **P4 拆分家族母单可被直接取消**：cancelOrder 无 parentCode 限制，母单取消后其状态不在聚合 units 中可见 → 产生"母单已取消但子单在履约"的暗箱矛盾 → 建议母单禁止直接取消或级联
   - **P5 履约状态双口径**：详情页同时展示 `stageOfOrder`（时间线档）与 `fulfillStateOf`（包裹档），部分妥投时前者显示"运输中"后者显示"部分妥投" → 同单两药丸不一致；建议 stage 推导也按包裹（对齐 selfStageOf 做法）
   - **P6 结算语义两处过载/口径待确认**：settleOnTime 既是"是否按时"又当"是否已结算"标记用；结算分母含未发货(shipped)包裹——补发货包会使已结算比例倒退 → 待业务确认分母口径
   - **P7 开票状态无依据联动**：invoiceStatus 纯手工 partial/full，无金额/发货单关联，未发货也可开票 → 建议关联发货单或金额、前置条件定为已确收
   - **P8 聚合数值分母不一致**：x/y 中 total 含已取消履约单（`distributed/{total}`），与聚合文本的 active 口径不齐 → 统一为 active 分母
   - **P9 rejected 死枚举**：终端有"已驳回"TAB 但无任何写入者（退回走 partnerReturnOrder 回 pending）→ 清理或补写入链路
   - **P10 弱类型标签表**：EXTERNAL_STATUS_LABELS/COLORS 为 `Record<string,…>`，拼写错误编译期不报 → 改 `Record<ExternalProcessStatus,…>`
4. **改进建议与优先级**（对应 P1-P10：立即修 / 近期修 / 待业务确认三档，标注涉及文件）
5. **待业务确认清单**（结算分母、开票前置条件、确收后取消是否走退货、母单取消策略）
6. **附录：合法状态组合矩阵**（分发×履约×结算可组合表 + 流转图文字版）
